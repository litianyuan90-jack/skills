# 安全迁移评审（Safe Migration Review）

迁移出事，很少是因为"复制错了"，更常见的是**有人还在往旧位置写**、**错误被吞掉了**、
**切换顺序反了**。这个 Skill 的目标是：在动任何东西之前，把这三件事查清楚，
并产出一份人可以直接拍板的方案。

## 铁律

1. **先只读，后动手。** 评审阶段不迁移、不提交、不改库、不停任务。需要修改时，
   列出来等人确认。
2. **没有校验过的备份，不算备份。** 备份必须放在迁移路径之外（例如不在 iCloud
   同步目录里），并用哈希核对。
3. **每个写入方都要有去处。** 迁移对象的每一个写入者，在切换后要么跟着搬、要么停掉、
   要么明确改指向。不能有"还在往旧地方写"的孤儿。
4. **不信任"没报错"。** 找出所有会吞掉错误的地方，切换期间把它们变成会响的。
5. **决定权在人。** AI 负责证据和选项，人负责选择、时间和执行分工。

## 流程

### 第 0 步：界定范围

写清楚：迁什么（路径、仓库、任务名）、从哪到哪、为什么迁、谁是决策人、
谁在哪台机器上执行。范围不清就先问，不要猜。

### 第 1 步：备份并校验

- 在迁移路径之外建立完整副本，包括版本元数据（如 `.git` 目录）。
- 对关键文件和整体内容做 SHA-256 校验，确认源、副本、目标三方一致：

  ```bash
  # 关键文件逐一核对
  shasum -a 256 "<源>/重要文件.docx" "<副本>/重要文件.docx"
  # 整库清单比对（排除系统噪音后再 diff）
  (cd "<源>" && find . -type f ! -name .DS_Store -print0 | sort -z | xargs -0 shasum -a 256) > /tmp/src.sha
  (cd "<副本>" && find . -type f ! -name .DS_Store -print0 | sort -z | xargs -0 shasum -a 256) > /tmp/dst.sha
  diff /tmp/src.sha /tmp/dst.sha
  ```

- Git 仓库额外核对：`git fsck`、`git status`、`git log -1`、各分支 HEAD 一致。
- 记录差异中的"噪音"（`.DS_Store`、Office 锁文件 `~$*`、插件缓存如 `.smart-env`），
  作为后续 `.gitignore` 调整的候选，**不要在评审阶段直接改**。

### 第 2 步：盘点所有读写方

对迁移对象，找出**谁在读、谁在写、什么时候、在哪台机器上**。常见来源：

| 类型 | 去哪里查 |
|---|---|
| macOS 定时任务 | `launchctl list`、`~/Library/LaunchAgents/`、`/Library/LaunchDaemons/` |
| cron | `crontab -l`、`/etc/cron*` |
| 仓库内脚本 | `_工具/`、`scripts/`、`bin/` 等目录，以及 hooks（`.git/hooks/`） |
| 同步工具 | iCloud、Dropbox、Syncthing、Obsidian Sync、Git 自动提交插件 |
| 应用/插件 | 笔记软件插件、索引服务、备份软件 |
| 外部数据源 | Apple 备忘录、语音转写、邮件、API 拉取 |

对每个脚本，读清楚它的：**输入来源、写入路径（是否硬编码）、运行机器、
触发时间、依赖的权限**（如 macOS 的"完全磁盘访问"、备忘录数据库访问），以及
**它在目标机器上是否能拿到同一份输入**。

产出一张依赖表：

| 名称 | 机器 | 触发 | 读 | 写 | 硬编码路径 | 目标机可用？ |
|---|---|---|---|---|---|---|

### 第 3 步：找出静默失败点

逐行找会把错误藏起来的写法，尤其在自动提交、同步、备份脚本里：

- `|| true`、`|| :`、`set +e`、`2>/dev/null`、`>/dev/null 2>&1`
- `try: ... except: pass`、空的 `catch {}`
- 没有日志、没有告警、日志写到没人看的地方的定时任务
- 退出码被忽略的管道（未设 `set -o pipefail`）

对每一处说明：**失败时会发生什么、多久后才会被发现、会不会导致数据分叉**。
例如：`git add -A && git commit ... || true` 在仓库已搬走或冲突时会静默失败，
导入的内容可能只留在旧机器上。

### 第 4 步：排切换顺序

原则：**写入方和它写入的存储一起切，或者写入方先停、后切**。不要让存储先走、
写入方留在原地。

写出有序步骤，每一步包含：执行人、机器、命令或操作、验证方法、回滚方法。

```
1. [人/MacBook] 暂停写入任务 A、B（launchctl bootout …）  验证：launchctl list 无此任务
2. [执行者/MacBook] 最终一次提交并推送/复制                 验证：两侧 HEAD 与哈希一致
3. [执行者/Mac mini] 部署任务 A、B，改写路径                 验证：手动触发一次并检查产出
4. [执行者/Mac mini] 恢复定时                               验证：次日产出与快照检查通过
回滚：任一步失败 → 停 Mac mini 任务 → 从第 1 步备份恢复 → 重启 MacBook 任务
```

如果目标机器拿不到同一份输入（例如 Mac mini 读不到同一份备忘录/语音），
这就是**阻断项**，必须先解决或改方案，不能进入执行。

### 第 5 步：反方评审

换一个视角（另一个 AI、另一个人，或自己刻意扮演反对者）专门回答：

- 如果只迁一半，会坏在哪里？
- 哪一步最难回滚？
- 有没有漏掉的写入方？（再查一遍第 2 步的每一类来源）
- 切换窗口内产生的新数据会落在哪里？
- 权限、时区、路径大小写、文件锁、同步冲突会不会在目标机器上表现不同？

反方意见要么被证据驳回，要么变成方案里的一步或一个阻断项。

### 第 6 步：交给人决策

输出下面的报告，然后停下，等待确认。

## 输出模板

```markdown
# 迁移评审：<对象> 从 <源> 到 <目标>

## 结论（一句话）
可以迁 / 暂不可迁（阻断项：…） / 需要改方案

## 当前状态
- 备份：位置、时间、校验结果（SHA-256 一致 / 差异列表）
- 版本元数据：HEAD、分支、fsck 结果

## 依赖表
| 名称 | 机器 | 触发 | 读 | 写 | 静默失败点 | 目标机可用？ |

## 风险
| 风险 | 触发条件 | 后果 | 发现时间 | 缓解 |

## 切换步骤
（有序，每步含执行人、机器、验证、回滚）

## 需要人决定的事
1. 是否按此方案迁移？
2. 执行时间窗口？
3. 分工：哪一侧由谁执行？
4. 后续清理项（如 .gitignore 调整）是否一并做？

## 不在本次范围
（明确列出，避免顺手改动）
```

## 双 AI 协作约定（可选）

两个 AI 在同一对话里协作时：

- **每条发言先说明身份**（"我是 Claude。""我是 Codex。"），并说明自己负责哪台机器、哪一侧。
- **一方提方案，另一方默认担任反方**，逐条回应，不能只写"同意"。同意时要补充证据，
  反对时要给出具体的失败场景。
- **越界操作要先声明**：任何非只读操作都要先在对话里写明，并等人确认。
- **分歧交给人**：两方意见不一致时，各自用一句话写出立场和证据，由人决定。

## 常见坑

- 只迁了 Git，自动导入任务还在旧机器上提交。
- 备份放在正在迁移的同步目录里，一起被同步覆盖了。
- 目标机器缺少"完全磁盘访问"等权限，任务能跑，但读到的是空数据。
- 两台机器同时开着同一个定时任务，产生双写和冲突。
- 把缓存、锁文件和系统文件一起迁过去，然后被提交进仓库。
- 切换当天的数据没人负责：旧机器停了，新机器还没开始。
